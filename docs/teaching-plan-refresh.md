# 年間指導計画の「改訂チェック & 差し替え」機構（拡張版機能）

教科書が改訂された時（おおむね4年ごと）や年度更新の際に、**1コマンド／将来はアプリのボタン1発**で、

1. 各社の年間指導計画の配布元を再取得し、前回から **変わっていないかをチェック**、
2. 変わっていれば差分を示し、**新年度パッケージ（拡張パック）の雛形を生成**、
3. 自動取得できないもの（要ログイン・学校から請求・ブラウザ操作要）は **ユーザーがやるべき行動を提示**

を行うための仕組み。**本体アプリには手を入れず**、拡張版機能として `feature/teaching-plan-refresh` ブランチで実装している。現状は CLI／Claude から実行する先行実装で、将来アプリ内のサービス層へ移植する。

## 構成

| ファイル | 役割 |
|---|---|
| `scripts/refresh_teaching_plans.py` | エンジン本体（取得・改訂検知・要対応提示・パッケージ生成） |
| `docs/teaching-plan-acquisition.json` | 機械可読の取得元ドライバ（エンジンが生成。編集は `DRIVER` を正とする） |
| `docs/teaching-plan-sources.yaml` | 人間可読のマスター（URLパターン・解析規則・落とし穴） |
| `verification/refresh-state.json` | 基準フィンガープリント（sha256）。差分検知の起点 |
| `verification/refresh-report.json` | 直近の実行結果スナップショット |

## 使い方

```bash
# 改訂チェック＋要対応レポート（自動取得社はフィンガープリント比較）
python3 scripts/refresh_teaching_plans.py check

# ネットに出ず、分類と時数バリデーションだけ
python3 scripts/refresh_teaching_plans.py check --offline

# 現在の配布元を「基準値」として保存（次回からこの状態との差分を見る）
python3 scripts/refresh_teaching_plans.py baseline

# 令和N年度(西暦)パッケージ雛形を生成（拡張パック形式）
python3 scripts/refresh_teaching_plans.py package 2028
```

Claude に対しては「**指導計画の改訂チェックを走らせて**」と頼めば `check` を実行し、結果の要対応・変更ありを解釈して次の取得作業まで引き継げる。

## 取得方法の分類（`method`）

| 記号 | method | 意味 | リフレッシュ時の扱い |
|---|---|---|---|
| 🟢 | `auto` | 直リンクを curl 取得 | フィンガープリントで改訂を自動検知 |
| 🌐 | `browser` | JS-SPA 等。Chrome拡張でDL | ユーザー/Claudeがブラウザ操作後に再解析 |
| 🔒 | `login` | 会員ログイン必須 | **ユーザーにログインを依頼** |
| 🏫 | `school_request` | 公開されず学校の立場で請求 | **ユーザーに学校からの請求を依頼** |

## いま要対応の2件（恒常的に発生しうる）

### 🔒 東京書籍『道徳』— 要ログイン＋既知の差し替え不具合
- 東書Eネットは会員ログイン必須。未ログインだと1年以上前の資料はDL不可。
- **既知不具合**: 5年の細案ページ `detail/118720` が6年ファイル `2024069240.docx`（中身が【6年】）に差し替わっており、**5年が取得できない（現状欠番）**。営業担当へ修正依頼が必要。
- 対応: ユーザーがEネットにログイン → Claude が再取得。5年は営業対応待ち。

### 🏫 信州教育出版社『生活』— 学校から請求（毎年度再発の可能性）
- 公開資料は「中心活動別の計画例」のみで、単元×配当時数の確定表がない。
- 対応: 学校の立場で「時数入りの正式な年間指導計画」を請求。
- **請求しても時数入りが得られない場合**は取得不能として扱い、ユーザー入力 or 他社流用で代替する旨をユーザーに伝える。この種の手動請求は教科書改訂のたびに再発しうる。

> エンジンは `recurring: true` のものを「（毎年度再発）」と明示する。同種の手動請求が今後も発生する場合、その旨が `check` の出力に常に表示される。

## 教科書改訂時の標準ワークフロー

1. `python3 scripts/refresh_teaching_plans.py check` を実行。
2. **⚠️変更あり**の社・教科 → Claude に「○○の△△を再取得して差し替えて」。`docs/teaching-plan-sources.yaml` の解析規則に従って再生成。
3. **🔒/🏫/🌐** → 提示されたユーザー行動（ログイン／学校請求／ブラウザDL）を実施後、再実行。
4. すべて反映したら `package <西暦>` で新年度パッケージを生成し、アプリの「パックを読み込む」から配布。
5. 取り込み後に `baseline` を実行し、次の改訂サイクルの基準を更新。

## アプリ内「取得ブラウザ」（CLI不要）

CLI を触らなくても、アプリの指導計画画面のツールバー「**取得ブラウザ**」ボタンから実行できる。

- UI: `client/src/components/TeachingPlanRefreshDialog.tsx`（クライアント: `client/src/lib/teachingPlanRefresh.ts`）
- バックエンド・ブリッジ: `server/refreshEngine.ts` が `scripts/refresh_teaching_plans.py` を子プロセス起動。
  - dev（Vite）: `vite.config.ts` の `refreshApiPlugin`（middleware）。
  - 本番（express）: `server/index.ts` の `/api/refresh/:action`。
  - エンドポイント: `GET /api/refresh/health|sources|run`。`run` が配布元を再取得して改訂検知。
- 表示: 校種タブ → 教科ごとに社カード。各社のステータスを
  - 🟢 **変更なし** / ⚠ **変更あり**（→ Claude に再取得依頼の文言を表示）/ ⏳ **取得中**
  - 🔒 **ログインが必要**（[ログイン]ボタン → 配布元のログインページを新規タブで開く）
  - 🏫 **学校から請求**（毎年度再発バッジ）/ 🌐 **ブラウザ操作**（[サイトを開く]ボタン）
  - ★欠番（例: 東京書籍 道徳5年）も明示。
- API が無い静的配信環境では「この環境では取得を実行できません」と案内（公開デモでの誤操作防止）。Mac/iOS ラッパーからは同じ HTTP API を叩けばよい。

## 校種の拡張（中学校など）

`DRIVER`（`scripts/refresh_teaching_plans.py`）の各エントリは `level`（既定 `"小学校"`）を持つ。
中学版を作る時は **中学校の発行者×教科を `level: "中学校"` で追記するだけ**で、UI に「中学校」タブが自動で増え、同じ改訂チェック・要対応提示・パッケージ生成が効く。標準時数（`STANDARD`）も校種別に拡張する。

## 将来のアプリ同梱像
- 拡張機能パネルに常駐させ、`auto` 社はバックグラウンドで差分検知、要対応はカード提示。
- 生成した新年度パッケージは既存の ExtensionPack ローダー（`{version,packId,name,templates}`）でそのまま取り込める。
